## 开发与评审过程中发现并修复的问题

前 6 项由作者在开发过程中发现，第 7–12 项由两轮独立只读评审（仿真内核评审、需求覆盖与声称审查）发现，第 13–17 项由本轮的浏览器视觉验收发现：

1. **物料守恒口径错误**：最初把仍在进货货车上的料包计入「在厂」，导致守恒式在班次前段不成立。现已把在途货车排除在厂口径之外，并在测试注释中写明理由。
2. **时钟与状态差一步**：`stateAtStep(0)` 曾返回「执行一步之后」的状态，与时钟 0 秒语义不一致。现明确「步数 0 即初始状态」。
3. **班次时间预算过紧**：第一版 150 秒时刻表下混纺打包块来不及装车、杂项回程未完成。调整为 130 秒并重排门岗、上线与打包时刻。
4. **存储区计数器未回退**：叉车从存储区取货时只改物料状态，没有减少存储区计数，班末残留假数据。已在取货环节同步回退。
5. **无障碍缺陷（由组件测试发现）**：时间轴里程碑按钮曾被放在 `aria-hidden="true"` 容器里，对辅助技术不可见。已移除并注明原因。
6. **测试自身缺陷**：用超出 `min/max` 的值去 `change` 一个 range 输入会被浏览器钳制，断言拿到的是钳制后的值。
7. **班末无兜底导致班次无法闭合**：把给料速率或带速调低后，料包会滞留在料斗里，班末残留物料。现改为「给料速率自适应 + 班末清场兜底」，并新增断言证明默认参数下无需清场即闭合。
8. **动态取货破坏了卸货**：把回程装车任务改成「到达时收取现场物料」后，卸货阶段也用同一套过滤条件，导致已装车的料包匹配不到、永远卸不了货（被清场掩盖）。现改由叉车记录在载货物，装卸两侧使用同一份事实。
9. **清场与归位互相打架**：清场每一步都执行一次，会把正在归位的叉车反复拉回待命状态；另有排队任务复活已出厂打包块的问题。现清场只执行一次、作废全部未完成任务，并禁止清场后新建任务。
10. **紧急停机让清场失效**：停机分支在清场之前 `return`，导致停机班次永远无法把空厂交接给下一个循环。现已把清场提前到停机判断之前，并在停机时直接把叉车归位。
11. **暂停时切换异常开关无反应**：异常标志原本只在推进步进时从设置同步到状态，暂停时切换「紧急停机」不会反映到状态与报警上。现改为在每次步进、跳转与重放后都同步。
12. **术语与文案**：设备曾只有完整英文名而不符合「英文缩写」的约定（现补 `DEVICE_ABBR`）、上下游关系显示内部 ID（现显示中文设备名）、料仓满溢预警开关原本不产生任何行为（现把报警线提前一包）、时间轴里程碑时刻与实际仿真不符（现已按实测定值并加测试锁定）。
13. **相机按钮压住时间轴**（浏览器视觉验收发现）：相机按钮组用固定 `bottom: 104px` 浮在场景左下角，而时间轴是同一区域的浮层；事件流从 1 行涨到 2 行时时间轴长高 58 px，两者重叠 32×12 px，结果 5 个里程碑标签与进度条被按钮盖住，实测 `俯瞰全厂` 与 `进货车辆入场` 重叠 46×9 px。现已把场景区改为纵向 flex（画布占剩余高度、时间轴作为独立底栏排在画布下方），相机按钮留在画布左下角，二者不再共用同一块像素。
14. **里程碑标签互相压字**（同上）：15 s / 20 s / 24 s 三个里程碑在 130 s 班次里相距不到 3%（1440 px 下仅 24–31 px），而标签宽 62 px，实测两两重叠 32×12、38×12、8×12 px，叠成一团乱码。现按导轨实测宽度做贪心分行（每行 13 px），刻度线用 `--mark-lift` 从导轨向下延伸到各自那一行；修复后 1440/1024/900/390 px 四档宽度的两两重叠均为 0。
15. **窄屏布局互相压盖**（同上）：≤820 px 时三栏本应堆叠、由页面统一滚动，实际 `.device-list` 被 flex 压成 24 px 高（设备列表只剩一条边）、`.app-stage` 被压成 0 高而内部 54vh 的场景溢出到外面、`.app-side` 因此直接叠在场景上，整片内容混在一起。现给三块显式 `flex: none`、设备列表限高 240 px，由 `.app-shell` 统一滚动；390×844 下三块依次排列、无任何重叠，也没有横向溢出。
16. **时间轴被挤出视口底部**（同上，由 13 的改法引出）：桌面三栏同处一行时行高是 `auto`，会随内容长高，事件流两行时 `.app-stage` 达 899 px 而可用高度只有 841 px，时间轴底部（946 px）落在 900 px 视口之下，事件流最后一行被裁掉。现把该行钉成 `minmax(0, 1fr)`（窄屏换多行布局时再改回 `auto auto`）。
17. **窄屏文案重叠与料仓名截断**（同上）：≤820 px 时 `场景操作提示` 与 `材质图例` 都在画布顶部同一行，实测重叠 48×15 px；料仓水位行的材质名用的是完整英文（POLYESTER 59 px 挤在 46 px 列里被截成 `POLYESTE`）。现窄屏下把图例移到提示下方，并把料仓名统一为与看板表格、场景图例一致的短名（PET / HDPE / 棉 / 涤纶 / 混纺，完整写法留在 `title`）。

## 画质升级：从「低多边形平涂」到「程序化微缩沙盘」

客户反馈「建模比较简陋，其他子项目都很精美」，据此做了一轮画质改造。硬约束不变（零外部图片 / 模型 / 字体 / CDN），新增依赖一个：`@react-three/postprocessing` 3.2.0（含 `postprocessing` 6.39.5）。

**动手前的诊断**（用代码计数说话）：场景只有 96 个 `<mesh>`、4 个建模文件共 648 行、每个设备平均 3–4 个基础体；整个厂房 101 行 = 地板 + 四面墙 + 屋顶；`<Canvas>` 没开 `shadows`，于是代码里那 1 处 `castShadow` / 1 处 `receiveShadow` 全部空转；没有 `scene.environment`（`metalness` 无物可反射）；没有雾与背景色；全场景只有 3 处 emissive；50 处内联材质各写各的十六进制色。对照兄弟项目（warehouse 1097 mesh、sakura 单件资产 127–674 行、boeing 有 PMREM 环境光 + 三点光 + 2048² 阴影）可见差距在**光与构件密度**，不在多边形数量。

**改了什么**：

| 层 | 内容 |
| --- | --- |
| 光 | `<Canvas shadows="soft">`；三点光（暖主光 3.6 投影 + 冷轮廓 0.36 + 暖补 0.24 + 半球 0.1 + 环境 0.035）；2048² 阴影贴图、`normalBias`；`RoomEnvironment` + PMREM 环境光（0.15）；雾与背景同色（`#6d7a84`，比地坪更深）；`toneMappingExposure` 1.0（二轮验收后按对比度重新配比） |
| 后处理 | Bloom（阈值 0.82 / 强度 0.5，只吃自发光）+ Vignette；吊顶灯带、状态指示灯、控制柜屏幕、门楣灯由此产生光晕 |

第三轮改完后按要求再做一遍完整验收，重点看「灯具移除 / 提亮增艳 / 布局重排」有没有留下副作用。结果是**又抓到两个真 bug**，都当场修了。

**做法**：全新会话（`mrf-r6`），`npm run preview` 的生产构建；视口 `1440×900` / `1180` / `1024` / `820` / `390×844`；状态覆盖 0.0 s、42 s 中段、100 s 班末、干预、实体屋顶、自由视角拖拽后切回俯瞰、窄屏首屏与滚到底。为避免浏览器拿缓存，切版后用带查询串的 URL 重新打开页面（这一条很重要：普通 `reload` 会继续用旧 JS，会导致「改了看不见」的假象，本次排查中就踩过一次）。

运行时卫生：页面错误 0、控制台 0、同源请求 3 条全 200，无外部主机、无 favicon 404。几何复核：里程碑标签 8 个两两零重叠（1440/1180/1024/820/390 一致），相机按钮底边 776 px 与时间轴顶边 788 px 不重叠，1440 与 1180/1024 下 `document` 无幽灵滚动；390 下真实滚轮只推进 `.app-shell`（`scrollY` 恒 0、`scrollTop` 0→600），内容可全部滚达。亮度直方图（3D 画布区域）：0 s 首屏 p01 0.140 / p50 0.604 / p99 0.818、标准差 0.112、过曝 0.5%；42 s 中段 p50 0.602、暗部 6.4%；说明「提亮」没有把阴影冲掉。截图与上一版对同一状态的字节比对：0 s 首屏与当前构建**逐字节相同**，渲染仍是确定性的。

### 这轮发现并修复的 2 个问题

1. **部分皮带被整体平移出厂区（真正的穿模/错位）**：`DeviceShell` 是一个带 `position` 的 `<group>`，而皮带几何是用**世界坐标**算出来的。第三轮为了让高光谱/平铺机构/取件带的选择框落到正确位置，把它们的 shell 位置从 `[0,0,0]` 改成了设备中心——于是这些皮带又被平移了一次，落到厂房外西南角，画面上表现为 4–5 段「悬空在厂区外的传送带」。光选机 #1/#2、输送段、爬坡机本来就有同样的双重位移问题（只是被机身挡住不易察觉）。修法：给这些用世界坐标建几何的皮带套一层负位移 `<group>` 抵消 shell 偏移，并把 `legs` 补到 pass1/pass2/lanePet/laneHdpe/laneTail/平铺带/高光谱带上——顺带解决了「传送带悬空 0.9–1.9 m、下面没有支腿」的观感问题。
2. **`俯瞰全厂` 在用过自由视角后失效**：相机动画窗口用「模式 + 目标」做 key，而自由视角下该 hook 提前 `return`，`elapsed` 既不增长也不清零；切回俯瞰时 key 与上一次相同 → 窗口不重置 → 机位永远拉不回俯瞰位置（实测停在园区前场、贴地仰视）。修法：显式记住上一次的模式，切回非自由视角时清零窗口。修后同一操作序列（拖拽 → 俯瞰全厂）与初始首屏取景一致。

另外把「跟随选中设备」的取景窗口从 1.8 s 延到 3 s，抵消 OrbitControls 阻尼残留在窗口结束后继续推动相机的问题。

## 独立仓库与 GitHub Pages 部署（2026-10-19）

本项目从合集仓库的子目录**单独立项**：代码、发布产物与在线站点都独立于 `ai-demo`，同时 `ai-demo` 里的工作副本保留，首页卡片与 publication 测试继续联动。

- 仓库：[github.com/yuhaoxiong/recycling-mrf-digital-twin](https://github.com/yuhaoxiong/recycling-mrf-digital-twin)（Public，默认分支 `main`）
- 站点：<https://yuhaoxiong.github.io/recycling-mrf-digital-twin/>（Pages 的 `build_type=workflow`，强制 HTTPS）

**做法与踩到的坑**

1. `vite.config.ts` 早就写着 `base: './'`，所以同一份 `dist/` 既能挂在合集站点的 `/ai-demo/recycling-mrf-digital-twin/dist/` 子路径下，也能直接作为独立站点的根路径——这次没有改构建配置，只在 README 里补了说明。
2. 仓库内 `git init -b main`，作者身份用 GitHub noreply 邮箱。`.gitattributes` 固定 `* text=auto eol=lf`：本机 `core.autocrlf=true`，若不固定，工作区 LF 与索引里的 LF 会被反复判成「已修改」。`.gitignore` 忽略 `node_modules`/`*.tsbuildinfo`，但**保留 `dist/` 提交**——合集侧的内联预览与离线分发都依赖它，CI 另出一份干净构建用于发布。
3. 工作流 `.github/workflows/deploy.yml`：`checkout → setup-node 22（npm cache）→ npm ci → npm run build → npm test → configure-pages → upload-pages-artifact(dist) → deploy-pages`。**顺序必须是「先 build 再 test」**：`tests/dist.test.ts` 那 5 条「发布产物自包含」断言在 `dist/` 缺失时会被 `skipIf` 静默跳过（这是早前评审已经点出的问题），先构建才能让它们在 CI 里真正执行。
4. **Pages 要先启用再 push**：`configure-pages` 在 Pages 站点尚未创建时会直接失败。顺序改为「建空仓库 → `POST /repos/{owner}/{repo}/pages -f build_type=workflow` → 再 push」。
5. 两个纯环境坑：Git Bash 下 `gh api /repos/...` 的前导斜杠会被改写成 `C:/Program Files/Git/repos/...`（端点参数去掉前导斜杠即可）；`agent-browser set viewport` 必须在 `open` 之后执行，否则整个命令挂住直到超时。
6. 首发那次 Actions 全绿但带 `Node.js 20 is deprecated` 告警（`checkout@v4` 等被强制跑在 Node 24 上）。已升级到 `checkout@v7` / `setup-node@v7` / `configure-pages@v6` / `upload-pages-artifact@v5` / `deploy-pages@v5` 并重跑验证，告警消失，只剩一条 `ubuntu-latest` 将于 2026-10-19 迁移到 Ubuntu 26 的提示。

**结果**

- 两次运行全绿：`39211797350`（首版，构建 27 s + 发布 12 s）、`39211906915`（升级 action 后，构建 37 s + 发布 8 s）。
- `curl` 线上：文档 200 / 960 B，`assets/index-rcjUfvH1.js` 200 / 1342383 B，`assets/index-D6dRfcgS.css` 200 / 11026 B。
- 浏览器实测（`agent-browser --session mrf-live`，1440×900）：页面错误 0、控制台 0、同源请求 3 条全 200、无外部主机、favicon 无 404（是内联 SVG data URI）；`document.title` 与 `canvas` 存在；点「继续」后时钟推进到 7.3 s / 130。
- **线上首帧与本地 `desktop-01-initial.png` 逐字节相同**（md5 `7b73ea3ca67e571e375cee2dec4439f1`），说明部署链路没有引入任何差异。

**这条链路没做的事**：没有加自定义域名、没有上 CDN 或缓存策略（`index.html` 靠 GitHub Pages 默认的短缓存，`assets/` 是内容哈希文件名，天然可长缓存）、没有配 `404.html`（单页无路由，不需要）、没有做真实服务器（nginx/Docker）的部署脚本——若以后要迁到自有服务器，`dist/` 三个文件直接指向静态目录即可，注意 `try_files $uri /index.html` 与不要用 `file://` 打开。

## 未验证项

- 跨浏览器矩阵（Safari / Firefox）与真实触控手势未测；帧率是在 headless Chromium（ANGLE D3D11 / RTX 4070 Laptop）上测的，rAF 不受 vsync 限制，**122–151 FPS 是渲染上限而非屏幕刷新率，不能外推**到真机；显存占用与低端设备表现未测。
- 约 130 秒的完整班次动画未逐帧人工核对：只抽查了 0.0 s / 52.5 s / 100.0 s 三张静帧，并用 4 倍速播放观察了整体连续性。
- 相机手感（自由视角拖拽、`跟随选中设备` 的推进动画）需要真人在真实鼠标下体验才能评价，本轮只确认了按钮状态与构图。
- 「微缩沙盘」观感只经过作者与自动化截图核对，未做多人主观评价；亮度直方图只能证明「不再浮白」，证明不了「好看」。
- 干预参数的取值范围只做了物理意义下的约束（例如气吹压力 2–8 bar），未与真实设备参数标定比对。
- 箱体/圆柱等几何的相互穿插没有做连续碰撞检测，只有「同一时刻可见物料不重叠」的抽样断言。
- 构建产物 1.34 MB（gzip 379.35 kB）未做拆包优化；若要继续压缩，`postprocessing` 与 three 是最值得拆的两块。

以上未验证项在 [README](../README.md) 的「验证与边界」一节也做了对外说明。发布产物的权威结果以 GitHub Actions 的运行为准。
